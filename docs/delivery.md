# Team Auto delivery

The automatic Plan → Code → Tests → Review pipeline does not finish at a passing review. It records a delivery question, shown in the existing inline response card in the Team conversation. The options are PR (recommended) and local main integration. This applies to plan, final and autonomous validation policies. A generic `go`, plan approval, native tool auto-accept or silence never selects a delivery method.

The question and answer persist in the workflow's clarification history. The user can select an option in the card or reply exactly `PR` or `main` in the composer. Other free responses return to planning without authorizing delivery. Pausing preserves the question; answering while paused records the choice but waits for resume. Changing the plan or explicitly restarting an implementation phase invalidates the previous delivery approval.

After explicit selection, Code receives a delivery-only turn with the task, build, review, tests, decisions, allowed repositories and launch context. It must preserve existing user changes and commit only changes whose ownership it can establish. It may create or reuse an open PR, committing and pushing its branch as needed. The main choice authorizes safe integration on local main; it does not authorize pushing main. Divergence, conflicts or changes needed during integration require a blocker and renewed validation. The delivery turn must not edit implementation files.

The plugin checks the repository fingerprint again before accepting the answer and checks file contents before dispatch and after delivery. File hashes are canonicalized so staging and committing new files do not invalidate unchanged content. A delivered result must include one exact commit receipt for each selected repository. Changed files must exist in that commit (or be deleted as validated), with no uncommitted workflow changes. Commit changes outside the validated diff are rejected. For main, the reported commit must be local main. For a PR, the GitHub CLI independently checks that the PR is open, belongs to the selected repository and has the reported head commit. This requires an authenticated `gh` command on the daemon host.

Only verified delivery changes the mission to completed. Missing credentials, malformed reports, changed content, incomplete multi-repository delivery or failed verification leave it at an attention checkpoint. There is no automatic retry after a delivery blocker; explicit resume reconciles or retries the saved delivery turn and its approved method. Existing operation IDs and receipts prevent an uncertain send from being replayed. Closing a workflow remains an explicit abandonment action; it does not display a successful mission summary.

This stage belongs to the automatic Team Auto pipeline. User-authored graph definitions retain their explicit step and terminal contracts; graph completion is separate from Team Auto mission delivery. Existing completed records remain historical. Older final checkpoints acquire the delivery question when approved, after their saved review and test fingerprint are checked.

Validation uses temporary Git repositories and simulated harness/GitHub responses. It does not publish a real PR or modify the user's main branch during tests.
